Unitree Robotics Program: Technical Summary

Overview

I built a working sim-to-real reinforcement learning pipeline for a Unitree Go2 quadruped. I trained a walking policy in NVIDIA Isaac Lab, validated it in MuJoCo, and deployed it to the robot's onboard computer. On 21 October 2026 the robot walked on hardware using my policy.

I led the evaluation, procurement and commissioning of two robots for STEM Innovation Academy (Calgary):

Robot Model Name Status
Quadruped Unitree Go2 EDU U3 Kepler Custom RL policy running on hardware
Humanoid Unitree R1 Edu Pro C Vera Commissioned; SDK motion, arm actions and dexterous hands working

The goal is instructional. Students will learn robotics through SDK programming, ROS and reinforcement learning, not through vendor demos. I am building my own fluency on both platforms first, and the curriculum follows from that.

Training and validation run on one Windows machine. Only the 758 KB policy and its config cross to the robot.

Hardware and infrastructure

I specified and set up a Windows-only workstation and avoided a dual-boot setup. Training runs natively on Windows, validation runs in Python, and deployment runs on the robot's own computer.

Component Specification
Workstation CyberPowerPC, NVIDIA RTX 5080 (Blackwell sm_120, 16 GB VRAM), Windows 11
Simulation stack Isaac Sim 5.1.0, Isaac Lab 2.3.2, Python 3.11, PyTorch 2.7 (CUDA 12.8)
Validation MuJoCo 3.13 with onnxruntime
Kepler onboard computer NVIDIA Jetson, Ubuntu 20.04, aarch64, CPU-only inference
Vera onboard computer Jetson Orin NX, JetPack L4T R35.3.1, ROS 2 Foxy, 16 GB RAM
Network Isolated wired robot subnet (192.168.123.0/24), no internet on the robot side

I mapped each robot's network myself. The two platforms use the same addresses for different roles. On Kepler, the Jetson is .18 and the motor control board is .161. On Vera, .161 is the control board and the Orin is .164, reachable only through the compute backpack's own port. Vera's backpack arrived with its power and network leads unconnected, and I found and fixed that during commissioning.

Simulation and training

I trained a velocity-tracking locomotion policy for the Go2 with Unitree's unitree_rl_lab on Isaac Lab, using PPO through RSL-RL. The policy is a 512/256/128 MLP, about 188,000 parameters, running at 50 Hz.

  • Run length: 23,043 of a planned 50,000 iterations. Reward plateaued near iteration 6,000, so stopping early cost nothing.
  • Episode outcomes: 99.7% ended at timeout, 0.2% on base contact, 0.1% on bad orientation.
  • Tracking error: 0.169 linear, 0.182 yaw.
  • Export: ONNX, 758 KB. Only the policy and its deploy.yaml go to the robot. The other 1.07 GB of checkpoints stay on the workstation.

I also imported Vera into Isaac Sim from the r1_description URDF. Unitree's Isaac Lab repo does not support the R1. I tracked a second first-party repo, unitree_rl_mjlab, which lists R1 support but has no worked R1 example yet.

Sim-to-sim validation and deployment

The policy passed 7 of 7 MuJoCo tests on flat ground before it went near hardware. I wrote a Python harness that runs MuJoCo and onnxruntime directly. That removed the need for WSL2, DDS and admin rights on the workstation. The harness resolves every joint by name, because Isaac Lab, the SDK and MuJoCo each use a different joint order.

Test Command Achieved
Stand 0 0.000
Walk forward vx 0.50 m/s 0.348
Walk fast vx 1.00 m/s 0.776
Walk back vx -0.50 m/s -0.324
Strafe left vy 0.40 m/s 0.247
Turn in place wz 1.00 rad/s 0.613
Arc vx 0.50 / wz 0.50 0.356 / 0.293

Body height held at 0.32 to 0.35 m. Peak torque was 21.6 Nm, under the 23.7 Nm hip limit. Every command tracked in the right direction at 60 to 78% of magnitude, which is the safe way to be wrong.

For deployment, I built Unitree's C++ controller (go2_ctrl) on Kepler's Jetson with the aarch64 build of onnxruntime and unitree_sdk2. I wrote a small service tool to release the motors from the factory controller over DDS, and a PowerShell script that redeploys a new policy and checks it by MD5 hash. On 21 October 2026, Kepler walked forward on my policy.

Problems I diagnosed and solved

None of these were documented, and most had misleading error messages.

Problem Root cause Fix
Controller aborted before main on every run The Jetson boots with 4 of 8 cores offline. onnxruntime indexes per-CPU data that only exists for online cores. I traced it with gdb to the library loader. Bring the cores online at launch
systemctl stop sport_mode could not free the motors The motor service runs on a separate control board with no shell Wrote a DDS tool using RobotStateClient to switch the service off
Shared libraries reported "file too short" Git on Windows saves symlinks as text files, and scp carried them across Recreated the links; moved files as tarballs from then on
Compile errors mixing SDK headers Factory SDK and new SDK ship incompatible CycloneDDS versions Installed the new SDK to a private prefix; rewrote the CMake to use find_package
First MuJoCo walks fell at 2 to 3 seconds The default scene contains a stair course Built a flat scene file; not a policy fault
Builds misjudged timestamps No real-time clock on the Jetson; it boots in 1970 Set the clock before every build
Turning sport_mode back on fails (error 5201) Unknown; possibly an SDK and firmware version mismatch Full power cycle restores it; raised with the vendor

Current status and next steps

Kepler walks forward on a flat-ground policy. Strafing was weak on hardware, and I traced it to the training configuration, not to the robot.

  • Strafe: the command curriculum capped lateral speed at ±0.4 m/s, 2.5 times narrower than forward. I am raising it to ±0.8.
  • Terrain: every rough sub-terrain in the training config was commented out, so the terrain curriculum never had anything to promote to. I am enabling slopes, stairs, boxes and rough ground for the next run.
  • Redeploy: a retrain is now four steps: edit the config, train, export, run the redeploy script. Nothing is rebuilt on the robot.

Vera is commissioned. I command locomotion states through the SDK's r1_loco_client, run 22 vendor arm actions, and drive the BrainCo dexterous hands over DDS. I wrote a safety rule for her: she never enters the RL locomotion state with her feet off the ground. Her RL path waits until Unitree's R1 support matures.

Curriculum direction: the pipeline I built maps to a student sequence. Students start with simulation and reward design in Isaac Lab, move to validation in MuJoCo, and finish with deployment to real hardware. Mapping the curriculum across both robots is the next phase.
